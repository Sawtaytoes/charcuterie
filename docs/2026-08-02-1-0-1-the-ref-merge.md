# 1.0.1 — a ref is not a value

**Branch:** `fix/1-0-1-slot-refs-compose`
**Gates**, re-run on the integrated result: lint (biome + eslint), typecheck, build, contrast
clear on all four variants x two schemes with **0** failing pairs, **508 tests over 74
files** (26 skipped; was 499 over 72 at M6f), `smoke:storybook` green on **151 entries** (was
150).

One behaviour fix, kept narrow on purpose. M6f fixed the *attribute* half of slot composition
and this is the half it left: the props that are not attributes.

---

## 1. The defect

`Menu` and `Tooltip` cannot share a trigger — image-viewer's report from M6c phase 2.

```tsx
<Menu
  isVisible={isVisible}
  items={BAY_ACTIONS}
  onDismiss={hide}
  trigger={
    <Tooltip label="Everything that can be done to this bay.">
      <Button onClick={toggle}>Bay 5</Button>
    </Tooltip>
  }
/>
```

Both components clone onto the trigger and both hand it a floating-ui `refs.setReference` —
the element each of them positions its panel against. Every merge in the library was
last-write-wins, so the inner `Tooltip` wrote its ref and the `Menu`'s was **gone**.

A menu with no reference element is not an error. floating-ui has nothing to measure, so it
leaves the panel at its initial `left: 0; top: 0` and the menu opens in the **corner of the
viewport**, three hundred pixels from the button that opened it. Nothing throws, the ARIA is
intact, `aria-expanded` still flips, axe is clean, and every existing test passes — the panel
is findable by role, it is simply in the wrong place. It reads as a CSS bug in the consumer.

**It was never one unlucky pair.** `useClonedChild` has four call sites — `Menu`, `Popover`,
`Tooltip`, `Field` — and three of them inject a `ref`. Any two of them on one control had
this.

## 2. Two places had the same hole

A `ref` is a **subscription** and an `on*` is a **listener**. Neither survives being
replaced, and both were being replaced, at two different levels:

| Level | What replaced what | Fix |
| --- | --- | --- |
| slot ↔ slot | `mergeSlotProps` settled M6f's five attributes and spread the rest, so the inner slot's `ref` won | `mergeSlotWiring`, spread last |
| slot ↔ **the element you wrote** | `cloneElement` replaces per key, so `<Menu trigger={<Button ref={buttonRef} />} />` dropped `buttonRef` | `mergeClonedProps`, inside `useClonedChild` |

The second was found while fixing the first and is the more embarrassing one: it means the
library silently discarded a *caller's* ref, on the element in their own file, in every
component with a trigger. Nobody reported it because a ref that is never called and a handler
that never runs both look exactly like nothing happening.

Both bindings have it. Preact's is a different mechanism with the same consequence — a ref
lives on the vnode rather than in props, and `cloneElement` resolves it as `ref || vnode.ref`
— so the Preact mirror puts the vnode's ref back alongside the props and merges one shape.

### The `WeakMap` is not an optimisation

Merged refs are cached in a `WeakMap` of `WeakMap`s keyed on the two refs being merged, so
the same pair always comes back as the **same function**. That is the difference between
working and hanging: React re-runs a callback ref whenever its identity changes between
renders — detaching with the old, attaching with the new — and both refs here are floating-ui
`setReference`s, which set state when called. A merged ref rebuilt each render would call
both twice per render, and each call schedules the render that rebuilds it.

`mergeSlotProps` is a plain function called during render, so it cannot reach for `useMemo`;
the memo has to live in the identity of the inputs. Handler chains are deliberately **not**
cached — nothing observes a handler's identity the way React observes a ref's, and
`getReferenceProps()` composes fresh functions on every call, so there would be nothing
stable to cache against.

### What did **not** change

Values still last-write-win. `Field`'s `id` beating the child's own `id` is the whole point
of `Field`, and `useClonedChild`'s fourth test pins it — the one test in the new file that
passes with the fix reverted, kept as the statement of the other half of the contract rather
than as a regression test.

## 3. Proven by reverting each half

M6f found a regression test in this exact area that **could not fail**, because it asserted a
value the component wrote unconditionally. So every assertion here was watched going red.

| Reverted | Test | Failure |
| --- | --- | --- |
| `mergeSlotWiring` out of `mergeSlotProps` | `a menu sharing its trigger with a tooltip is still anchored to it` | `expected +0 to be 64` — the panel back at the viewport origin while the trigger is at 64 |
| `mergeClonedProps` out of React's `useClonedChild` | `the slot's ref does not replace the child's own` | `expected [] to deeply equal [ <button> ]` — the caller's ref never called at all |
| " | `an object ref composes with a callback ref` | `expected null to be <button>` |
| " | `both handlers run, the child's first` | `expected [ 'slot' ] to deeply equal [ 'child', 'slot' ]` |
| `mergeClonedProps` out of Preact's | both of its tests | the same two failures |
| `readonly` off `SelectProps.options` | `yarn typecheck` | `TS4104` at five call sites in `Select.stories.tsx` — the consumer's own error |

**The assertion is geometry, because nothing else can see this.** `Menu` does not write that
number: floating-ui computes it from the reference element, so "the panel is where the
trigger is" is false exactly when the ref was dropped and true otherwise. There is no
attribute, no role and no class that differs between the two states.

Two things keep the geometry honest:

- **The story is padded**, and `expectAnchoredTrigger` asserts the padding is still there
  before it asserts anything else. An unanchored panel lands at the viewport origin, so a
  trigger at the origin makes both readings identical and the test passes for the wrong
  reason. This is the same shape as M6f's `LogViewer` test asserting `scrollHeight === 0` as
  an explicit precondition.
- **Only the main axis is asserted for the tip.** `shift({ padding: 8 })` legitimately moves
  a 229px tip over a 71px button near the edge, and an assertion loose enough to allow for
  that is one an unanchored tip would also satisfy. `bottom === trigger.top - 6` it cannot
  satisfy: unanchored reads `bottom 24`.
- **Both refs are asserted**, in two tests. A "fix" that reversed the priority instead of
  merging would leave the *tooltip* pointing at nothing, and the menu test alone would still
  pass.

## 4. Driven in a browser

Storybook built, served, and `components-menu--shared-trigger` driven to the state where
**both overlays are live at once** — hover the trigger, click to open the menu, hover back
onto the trigger so the tip re-opens while focus sits in the panel. Screenshots in
`__screenshots__/1-0-1-shared-trigger-{before,after}.png` (gitignored).

Measured on the page, trigger at `left 314.5, top 190, bottom 230`:

| | before | after |
| --- | --- | --- |
| menu panel | `left 0, top 0` | `left 315, top 234` — `trigger.bottom + 4`, `offset(4)` |
| tip | `bottom 184` | `bottom 184` — `trigger.top - 6`, `offset(6)` |

The tip is anchored in both, which is the defect stated exactly: the inner slot always won,
so the visible symptom was only ever the *outer* one being wrong.

## 5. The narrow scope, and what it left

`useClonedChild` is still `cloneElement`. Kevin: *"we probably shouldn't anymore, but i'll
leave that for later"* —
[decision](decisions/2026-08-02-useclonedchild-keeps-cloneelement-in-1-0-1.md), which records
why deferring beats half-starting it.

The four gaps M6's consumers reported and this release did not touch — `Field` overwriting a
child's own `id`, `Menu`'s missing point anchor and non-item states, `Badge`'s missing
`asChild`, `EmptyState`'s `headingLevel` cap — are collected with their workarounds in
[reported by consumers, queued for 1.1](2026-08-02-reported-by-consumers-queued-for-1-1.md),
along with the one internal debt this release created: `mergeRefs` exists twice because
sharing it means a new public export, and a new export is a `minor`.

## 6. Also in this release

**`SelectProps.options` accepts a `readonly` array.** image-viewer wrote its options table
`as const` and hit `TS4104`, then copied the array at every call site to get past it. The
component only ever `.map`s over the list, so the mutable parameter was asking for a
permission it never uses. Type-only, safe in a patch, and pinned by
`Select.stories.tsx` declaring its options `as const satisfies readonly SelectItem[]` — a
call site that fails `yarn typecheck` if the widening is ever reverted.
